Product requirements · draft for brainstorming

Acme invoice processing agents

A multi-agent prototype that reads messy invoices, checks them against inventory, simulates VP approval with a self-critique loop, and pays or logs a rejection. This page lists requirements only; the design is decided later.

Source README @ 2f15015Inputs 22 sample filesRepo doc docs/PRD.md
$2Mlost each year to manual processing
30%error rate today
5 daysfrom receipt to payment
$10Kthreshold for extra VP scrutiny

Problem

Invoices arrive by email as messy PDFs. Staff key in the data, check it against an inconsistent legacy inventory database, chase VP approval over email, and pay through a banking API. The prototype has to run locally, with every external service simulated.

Each requirement is tagged by where it comes from: brief stated in the README data implied by the sample invoices inferred needed for credibility, so a candidate to cut

Questions to brainstorm

Domain semantics · these change the core logic

B-1

What does "stock" mean?

Acme is buying, so an invoice that asks for more than Acme holds is not wrong in itself. Options: take the brief literally, or treat the table as purchase orders and goods received (a three-way match).

Lean Take it literally, and record the three-way-match reading as an assumption for later.
B-2

Revisions and duplicates

Does R1 replace 1004 or add to it? Are a PDF and a TXT copy the same invoice? Which copy wins?

B-3

Is stock stateful?

Should approved invoices reduce stock, so that batch order matters? Or is every invoice checked against the stock as seeded?

B-4

Partial approval

Pay the valid lines of 1016 and hold WidgetC, or reject the whole invoice?

B-5

Currency

Convert EUR at a fixed mock rate, or always escalate?

B-6

Price tolerance

How far can a unit price differ from the catalog (discount, rush, foreign currency) before we flag it?

B-7

Approval policy

Tiers at $10K and $50K? How much do vendor risk, a past-due date and a near-threshold total weigh?

Architecture

B-8

Orchestration

LangGraph (an explicit state machine that is easy to draw), CrewAI or AutoGen (more "agentic", less control), or a custom orchestrator (smallest). The grade rewards both sophistication and code quality.

B-9

Where the LLM decides and where code decides

Rules belong in code. The LLM handles extraction and narrative judgement. How much does it actually decide?

B-10

Ingestion strategy

A deterministic parser for each format with the LLM as fallback, or the LLM for everything with a schema check? This trades cost and determinism against the agentic look.

B-11

Shape of the self-correction loops

Extraction loops back on reconciliation errors; approval loops between a proposer and a critic. What are the iteration caps and the stop conditions?

B-12

Model

Grok if there is a key; otherwise another model behind one interface, plus a scripted offline client. The README's SDK snippet looks out of date, so check it.

B-13

PDF stack

All three PDFs have a text layer, so pdfplumber or PyMuPDF covers them. Do we also need OCR for scanned images?

Product and presentation

B-14

UI

Textual or Rich in the terminal, Streamlit, or FastAPI with HTMX. Should it have an approval inbox, a per-invoice trace and a "why" panel?

B-15

Going beyond the brief

Vendor risk score, a revision ledger, human override, trace replay, a cost dashboard, adversarial test invoices, an eval harness scored against the table above.

B-16

Business-impact story

Measure time per invoice, cost per invoice and catch rate on the trap cases, then project against the $2M and 5-day baseline.

B-17

How far to cut

What is the minimum loveable demo? Candidates to drop: XML and email intake, partial approval, a live UI.

Proposed out of scope: real email or banking integrations, cloud deployment, multiple tenants, authentication, and a real ERP or procurement system.
