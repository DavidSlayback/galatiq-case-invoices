Acme Invoice Agents

A multi-agent accounts-payable pipeline for Acme Corp. It reads supplier invoices in any of the formats Acme receives, checks them against inventory, prices, vendors and policy, and pays, rejects with reasons, or hands the case to a person with the evidence attached. The bet: agents copy values and make the judgement calls; code holds every rule that moves money.

What it does

Each invoice moves through one state graph. The extraction agent copies what the document says; code parses and checks it, and re-asks the agent when the totals do not add up. A ledger stops duplicates, keyed by one identity rule. Rules with stable IDs score the invoice, and a router sends it down one of four paths. Only judgement calls reach the VP agent, and an independent critic must agree before anything is paid. Every step appends to an event ledger that cannot be edited.

Worked example: invoice 1004 and its revision

  1. invoice_1004.json: the extractor returns 3 WidgetA and 2 WidgetB, subtotal 1750.00, tax 140.00, total 1890.00. The totals reconcile on the first attempt.
  2. The ledger has never seen Precision Parts INV-1004, so it records received and stores a content fingerprint.
  3. No rule fires: stock is fine, prices match the catalog, and the due date is 1 day off Net 30, within the ±1-day tolerance. The total is under $10K, so it is auto-approved and mock_payment pays 1890.00.
  4. invoice_1004_revised.json (revision R1) arrives, adding 5 GadgetX for a total of 5940.00. The ledger sees a higher revision of a paid invoice and writes superseded with the diff: GadgetX ×5, +4050.00.
  5. Because the original was already paid, R1 is never paid automatically. Only the 4050.00 difference goes to the inbox, and an approval with a note pays exactly that.

Decisions and tradeoffs

Agents copy, code parses

Agent
Chose
The extractor returns every value as written ("$3,500.O0", "26-Jan-2O26"). Deterministic code parses dates, amounts and SKUs.
Over
Having the model return typed numbers and dates.
Because
The arithmetic checks become exact and identical across models, and the recorded answers for offline tests stay honest.
Cost
The normaliser has to cover every format. An ambiguous amount raises and re-asks rather than guessing.
Revisit when
Invoices arrive in locales with comma decimals.

Rules in code, judgement in agents

David
Chose
Hard rules reject before any agent runs. The VP agent sees only judgement calls, a critic must agree, and a guardrail blocks approval with any hard finding.
Over
One agent reviewing every invoice, or self-reflection by a single agent.
Because
Money moves only on decisions that are deterministic or checked twice, and the agents spend tokens only where judgement is needed.
Cost
Two extra calls per judgement case. A deadlock goes to a person.
Revisit when
The live critic agrees often enough to trust a single reviewer.

Vendor changes go to a person

Agent
Chose
A renamed vendor (QuickShip, formerly FastShip) routes straight to the inbox.
Over
Letting the VP and critic judge it, which was the first design.
Because
Both live models approved it. Who gets paid is a vendor-master change that AP confirms with the vendor, out of band.
Cost
Every legitimate rename costs a human review.
Revisit when
The vendor registry records verified renames.

One identity rule

Agent
Chose
One module decides when two documents are the same invoice. Its folding rule is used in Python and registered as a SQLite collation on every key column. Aliases key under the registered vendor.
Over
Each module normalising names its own way, which the final review showed disagreeing.
Because
SQLite's built-in case folding covers ASCII only, so "Müller" and "MÜLLER" could both be paid, and an alias resubmission escaped the duplicate check.
Cost
Other database tools must register the collation, and older databases must be rebuilt.
Revisit when
The store moves to Postgres, where a stored folded key column replaces the collation.

Payments as an outbox

Agent
Chose
Write the payment as pending before calling the bank, and settle it after. An interrupted or timed-out call goes to a person; only a definite refusal is retried.
Over
Calling the bank, then recording the payment.
Because
A crash in between left no trace, and the next run paid again. Never paying twice is the first rule.
Cost
A slow bank call can put a payment in front of a person that turns out to have succeeded.
Revisit when
A real bank API offers idempotency keys.

Literal stock check

David
Chose
Invoiced quantity, summed per SKU, must not exceed stock, exactly as the brief asks.
Over
Reinterpreting stock as a purchase-order and goods-received match.
Because
It matches the brief's expected outcomes, and the README states the reinterpretation as the production path.
Cost
For a buyer, "more than we stock" is not wrong in itself.
Revisit when
Purchase-order data exists.

People teach the vendor registry

David
Chose
A reviewer who verified a rename or new bank details with the vendor can record it while approving. The vendor's next invoice is not flagged for it again, and the change is logged with their note.
Over
Asking a person about the same renamed vendor on every invoice, or letting a model update who gets paid.
Because
Escalations should fall as people decide. The opt-in keeps vendor-master changes a human decision (D33).
Cost
A careless tick would trust a vendor change. It is off by default, applies only to an approval, and is never offered for look-alike names.
Revisit when
Vendor changes need a second approver.

Read-only tools for the reviewers

David
Chose
The VP and critic can look up the vendor's record with Acme and the catalog, through two read-only function tools.
Over
Putting everything in the case brief, or giving the agents tools that act.
Because
Judgement calls need context the brief leaves out, and lookups that never write cost nothing in safety. The live run showed why each tool answer has to be explicit: an empty history once read as "unknown payee".
Cost
More model turns per review. Runs are capped at 8 requests, and a stuck run goes to a person.
Revisit when
Agents need tools that change state; those would need the same guardrail as payments.

Any model, or none

David
Chose
Recorded answers offline, any API key, or Grok and Claude through their CLIs on existing subscriptions, sandboxed.
Over
Requiring an xAI key to run at all.
Because
The brief assumes no internet, graders may have no key, and the subscription CLIs give a real Grok run with no API spend.
Cost
The xAI API path is configured but was not exercised live.
Revisit when
An xAI key is available.

What broke, and known gaps

The live runs and independent verifiers found real problems, and each one changed the system:

  • The first live VP rejected a harmless 2-day terms gap, and the critic rightly objected. The review policy now judges each flag on materiality.
  • Two invoices state wrong totals (1007, and 1013, which is $50 high). The reconcile step caught 1013 on its first run, although neither the brief nor the first review noticed it.
  • A review of the module refactor reproduced money bugs in five rounds: a payment a crash left half-done was never recovered, a revision hid an unconfirmed payment, an upgraded database paid an alias twice, and a slow bank call raced a reviewer's cancel. Each now has a regression test that fails if its fix is removed.
  • A final adversarial round, after the work was called done, found 18 more. A code review showed a look-alike invoice could rewrite the real vendor's bank details through the reviewer's "verified" checkbox, and that an alias's remit-to was never checked. A red team that could only send invoice files got money paid, paid twice or silently skipped 10 ways: freight overcharges, resends under INV-04010 or -A or no number, splits across days or in EUR, a remit-to that contained the real account inside a longer one, and disguised injections. Each is now a rule and a regression test (D52, D53); no sample outcome changed.
  • Fresh-context verifiers caught silent wrong values and denial-of-service paths in the untrusted parsers: 1.234,56 read as 1.23, UTF-16 XML getting past the entity ban, and a 200-inch PDF page using 4.6 GB.
  1. Literal stock check. A buyer needs a purchase-order and receipt three-way match. That needs PO data the brief does not provide.
  2. Approvals don't reserve stock. Every invoice is checked against the seeded stock, so batch order never changes an outcome.
  3. Bank idempotency. A crash or timeout never re-sends a payment, and every late send is recorded. Only a bank-side idempotency key stops two sends when a retry races a slow original; races of three or more attempts are untested.
  4. Reworded injection. Instruction text the injection rule does not recognise still reaches the VP and critic. Both rejected every such attempt in the red-team run, and the guardrail still blocks any approval that breaks a hard rule, but that is not a guarantee.
  5. xAI API not run live. It is configured and first in auto-detect, but untested without a key.
  6. Small, problem-heavy test set. Its 22% escalation rate overstates production. The ROI page says so and lets the presenter change every assumption.

Expected questions

Why not let the LLM decide everything?

Because the money-moving rules have to be the same every time. Stock, arithmetic, duplicates and the $10K and $50K tiers are code with stable rule IDs. The agents read messy documents and make the judgement calls the rules leave open, and a guardrail makes approving with a hard finding impossible.

How do you know the agents work, not just the replays?

Live runs on Grok 4.7 and Claude Haiku processed all 27 invoices. Both extractions matched the recorded answers exactly, and both read the scanned PDF from its image. The differences they did show changed the system: the vendor-change route, the date re-check, and stripping "(formerly …)" from vendor names. See docs/live/README.md.

What stops a prompt injection inside an invoice?

Three layers. The extractor is told that document text is data. A PROMPT_INJECTION rule flags instruction-like text whatever the model did with it. The rule folds look-alike letters, invisible characters, line breaks and base64 first, and knows French, Spanish and German forms. And no agent can approve past the guardrail. An earlier invoice number that is not a plain number is withheld from the lookup tools, so one invoice cannot plant instructions for the next. The CLI backends also run with tools off, in an empty directory.

What if the process dies in the middle of a payment?

The payment row is written as pending before the bank is called. Re-running the file is a duplicate, so a sweep before each run and each inbox listing finds pending rows older than two minutes and puts them in front of a person, who confirms the payment at the bank or cancels it for a retry. If the original then succeeds late, the store records it, so the vendor is never paid twice without the ledger knowing.

What if the process dies at a bad moment?

Every crash point has an owner. A pending payment older than two minutes goes to a person to check at the bank. An invoice a crash left mid-run is resumed by a re-run after 30 minutes, which exceeds a live run's worst case. A person's recorded decision is never re-judged; if a crash leaves it unsettled, it goes back to the inbox. Each case is a regression test that fails if its fix is removed (D45, D46).

What happens at 10x volume?

The graph is stateless per invoice, so it parallelises once SQLite becomes Postgres and a queue feeds it. The cost is about 4.6¢ per invoice on Grok, and much less on Haiku. The real limit is the human inbox, which is why the ROI page models review time explicitly.

What would another week buy?

Purchase-order three-way matching, stock reservation, an idempotency key at a real bank, and a live run on the xAI API.

Glossary
  • Golden: a hand-written record of what a faithful model returns for one file. Offline mode replays it.
  • Hard, soft, fraud, note: rule severities. Hard rejects, soft goes to the VP, fraud goes to a person, and a note is informational.
  • Outbox: a payment is recorded as pending before the bank call and settled after, so a crash leaves evidence instead of a gap.
  • Superseded: a higher revision replaces the original; if the original was paid, only the difference is due.
  • Vendor-master change: a change to who is paid, such as a rename or new bank details.
